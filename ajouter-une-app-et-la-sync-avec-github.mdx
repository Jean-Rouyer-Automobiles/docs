## Vue d'ensemble

Le principe :

- le serveur détient une paire de clés SSH dédiée à GitHub ;
- GitHub s'y connecte en SSH via **appleboy/ssh-action** à chaque push sur `main` ou `preview` ;
- le script de déploiement fait un clone ou un reset du dépôt dans `~/git/<repo>`, puis installe les dépendances Composer ;
- le dossier `public` de l'app est exposé au serveur web via un lien symbolique ;
- un `.htaccess` et un bootstrap `index.php` isolent le code exécutable.

Le déploiement utilise deux environnements GitHub :

| Branche | Environnement |
| --- | --- |
| `main` | `production` |
| `preview` | `preview` |

## 1. Préparation du serveur

Se connecter en SSH au serveur, puis créerer le dossier qui accueillera les clones git :

```bash
mkdir git
```

Créer une clé SSH dédiée pour GitHub :

```bash
ssh-keygen -t ed25519
```

Règles :

- **ne pas** renommer la clé (chemin par défaut `~/.ssh/id_ed25519`) ;
- **ne pas** mettre de passphrase (le déploiement est automatisé).

Ajouter la clé publique en clé autorisée :

```bash
cat id_ed25519.pub >> authorized_keys
```

## 2. Autoriser GitHub sur le serveur

Créer (ou compléter) la config SSH pour forcer l'utilisation de cette clé avec GitHub :

```bash
echo "Host github.com
 HostName github.com
 User git
 IdentityFile ~/.ssh/id_ed25519
 IdentitiesOnly yes" > ~/.ssh/config
```

Tester la connexion :

```bash
ssh -T git@github.com
```

Valider avec `Yes`. Le message attendu :

> Hi Jean-Rouyer-Automobiles/\<repo> ! You've successfully authenticated, but GitHub does not provide shell access

---

## 3. Ajouter la clé sur GitHub (deploy key)

Dans le repo GitHub : **Settings → Deploy keys → Add deploy key**.

- **Key** : le contenu **complet** du fichier `id_ed25519.pub` ;
- **Title** : l'identifiant de fin de la clé, sous la forme `<who>@<from>` ;
- la clé est en **lecture seule** (ne pas cocher _Allow write access_).

> GitHub n'a ainsi que le droit de lire le dépôt (clone/fetch), jamais d'écrire.

## 4. Configurer le workflow de déploiement

### Secrets et variables

Dans **Settings → Secrets and variables → Actions**, créer les environnements **`production`** et **`preview`**, puis y déclarer :

| name | type | description |
| --- | --- | --- |
| `SSH_HOST` | variable | URL ou IP pour la connexion SSH |
| `SSH_USER` | secret | utilisateur pour la connexion SSH |
| `SSH_KEY` | secret | clé privée SSH créée au §1 (le fichier **sans** le `.pub`) |

### Workflow

`.github/workflows/deploy.yml` :

```yaml
name: Deploy Backend via SSH

on:
  push:
    branches: [main, preview]


jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: ${{ github.ref_name == 'main' && 'production' || 'preview' }}
    steps:
      - name: Deploy via SSH
        uses: appleboy/ssh-action@v1
        env:
          BRANCH: ${{ github.ref_name }}
          REPO: ${{ github.event.repository.name }}
        with:
          host: ${{ vars.SSH_HOST }}
          username: ${{ secrets.SSH_USER }}
          key: ${{ secrets.SSH_KEY }}
          envs: BRANCH,REPO
          script: |
            set -e
            cd ~/git

            if [ -d "$REPO/.git" ]; then
              cd "$REPO"
              git fetch origin
              git reset --hard "origin/$BRANCH"
            else
              rm -rf "$REPO"
              git clone "git@github.com:${{ github.repository }}.git" "$REPO"
              cd "$REPO"
              git checkout "$BRANCH"
            fi

            cd apps/api
            composer7.4-sp install --no-dev
            composer7.4-sp dumpautoload -a
            echo "✅ Déploiement $BRANCH terminé"
```

À partir de là, le déploiement se lance à chaque push sur `main` ou `preview`.

> Le script gère deux cas : premier déploiement (clone) et déploiements suivants (fetch + `reset --hard`, qui écrase toute modification locale). Les dépendances sont installées en mode production (`--no-dev`) avec l'autoloader optimisé (`-a`).

## 5. Lier le déploiement au serveur web (lien symbolique)

La liaison entre le clone git et le serveur web se fait par lien symbolique.

**Important** : le dossier `public` du clone git doit exister avant la création du lien, mais **pas** le `public` dans `apps`.

```bash
pwd   # pour connaître le chemin complet du répertoire, ou utiliser ~/
ln -s <clone git>[/apps/api]/public ~/apps/<app name>/public
```

Exemple :

```bash
rm -rf ~/apps/api-cron/public
ln -s ~/git/jra-cron-legacy/apps/api/public ~/apps/api-cron/public
```

## 6. Bootstrap de l'app

Pour démarrer l'app en toute sécurité, un dossier `public` isole le code accessible depuis le web. Il reste deux choses à faire :

1. **interdire l'accès aux ressources parentes** ;
2. **créer le bootstrap** qui exécutera le code.

### `public/.htaccess`

```apache
RewriteEngine On
RewriteCond %{HTTP:Authorization} .
RewriteRule ^ - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]
RewriteRule ^index\.php$ - [L]
RewriteRule \.(php|phtml|phar|cgi|pl|py|sh)$ - [F]
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ index.php [L]
```

Rôles des règles :

- transmission de l'en-tête `Authorization` (nécessaire pour l'auth par token/Bearer en FastCGI) ;
- `index.php` servi tel quel ;
- accès direct à tout fichier exécutable (`.php`, `.phtml`, `.phar`, `.cgi`, `.pl`, `.py`, `.sh`) interdit ;
- toute autre requête routée vers `index.php`.

### `public/index.php`

```php
<?php
chdir(dirname(__DIR__));
require dirname(__DIR__) . '/index.php';
```

Le bootstrap remonte à la racine de l'app et délègue au `index.php` racine, hors du dossier public.
